* TODO Implement WebAssembly stack switching on x86_64 FreeBSD :freebsd:
  :PROPERTIES:
  :ID:       b2e3fe88-ebf6-4480-a601-c3aced81d4d4
  :ORGBUG_ID: 1
  :CREATED:  [2026-09-16 Wed]
  :END:
*Goal*

Implement and validate Wasmtime's experimental WebAssembly stack-switching proposal on =x86_64-unknown-freebsd=.

*Context*

- FreeBSD amd64 can build and run the broader Wasmtime workspace, but =Config::wasm_stack_switching(true)= is currently rejected.
- =crates/wasmtime/src/config.rs= and =crates/wasmtime/src/engine.rs= do not select a stack-switch model for FreeBSD.
- =crates/cranelift/src/func_environ/stack_switching/instructions.rs= currently defines the control-context layout only for x86_64 Linux.
- The continuation stack allocator already has an x86_64 Unix implementation under =crates/wasmtime/src/runtime/vm/stack_switching/stack/unix.rs=, and the fiber crate has x86_64 switching routines. These pieces must be audited rather than assumed to be ABI-compatible.
- The FreeBSD baseline currently treats failure to initialize this feature as an expected platform limitation in =tests/all/tags.rs=.

*Scope*

1. Document the precise platform gates and ABI assumptions for x86_64 Linux versus x86_64 FreeBSD.
2. Determine whether FreeBSD can use Cranelift's =basic= stack-switch model and the existing control-context layout; add a dedicated layout when required.
3. Audit continuation-stack allocation, guard pages, register preservation, stack alignment, native signal/trap handling, unwinding, and backtraces on FreeBSD.
4. Enable FreeBSD in the Wasmtime configuration and compiler checks only after those assumptions are validated.
5. Run the stack-switching unit, integration, and WAST suites on native FreeBSD amd64 through the vmactions CI workflow.
6. Remove the FreeBSD expected-unsupported condition once the feature works reliably.

*Acceptance criteria*

- =Config::wasm_stack_switching(true)= initializes on =x86_64-unknown-freebsd=.
- =tests/all/tags.rs= and =tests/all/stack_switching.rs= pass without a FreeBSD-specific skip or expected failure.
- Stack-switching WAST tests run instead of being filtered on FreeBSD and pass.
- Full FreeBSD 14.5 and 15.1 amd64 =workspace-debug= CI remains green.
- Any FreeBSD-specific ABI or signal-handling assumptions are documented next to the implementation.

*Out of scope*

- FreeBSD AArch64 support.
- Resolving the separate native host-stack-overflow diagnostic difference tracked by the strict =host_segfault= XFAIL.
- FreeBSD target-tier promotion or maintainer approval.

* TODO Investigate FreeBSD SIGSEGV in overrun 8k with misconfigured host :freebsd:
  :PROPERTIES:
  :ID:       f3bb9463-3846-4474-acf9-946d3e3521a1
  :ORGBUG_ID: 2
  :CREATED:  [2026-09-16 Wed]
  :END:
*Goal*

Determine why =FreeBSD SIGSEGV in overrun 8k with misconfigured host= and restore a controlled, correctly diagnosed stack-overflow result.

*Context*

The =host_segfault= harness deliberately tells Wasmtime that Wasm may use a 100 MiB stack, then executes the module on a native thread with only a 2 MiB stack. This intentionally misconfigured host must hit the native guard page deterministically.

On supported Unix paths, the original =SIGSEGV= or =SIGBUS= should be recognized as a stack overflow, produce a diagnostic containing =has overflowed its stack=, and terminate deliberately with =SIGABRT=. On FreeBSD amd64 the subprocess instead terminates directly with signal 11 (=SIGSEGV=), although stdout confirms that it reached the intended overflow path.

The FreeBSD workflow currently skips this exact case in the combined runtime invocation, reruns it alone, and requires the exact known =SIGSEGV= result as a strict XFAIL.

This issue tracks =overrun_with_big_module(8 << 10)= specifically. Related case: orgbug #3.

*Investigation scope*

1. Reproduce the isolated case on FreeBSD 14.5 and 15.1 amd64 through the vmactions workflow.
2. Identify whether the raw =SIGSEGV= comes from Rust's native stack-overflow handling, Wasmtime's signal/trap handler, alternate signal-stack setup, guard-page classification, or their interaction.
3. Verify the actual fault address against the native thread guard page and Wasmtime's registered Wasm stack limits.
4. Preserve the safety rule that Wasmtime must not intercept unrelated host segmentation faults.
5. Implement the platform fix or an upstream-approved FreeBSD-specific assertion, then remove this case's workflow-level strict XFAIL.

*Acceptance criteria*

- The isolated =host_segfault= test case passes natively on FreeBSD 14.5 and 15.1 amd64.
- The case runs inside the normal Wasmtime runtime test command without =--skip=.
- Its dedicated strict-XFAIL loop entry is removed from =.github/workflows/freebsd.yml=.
- The remaining =host_segfault= cases, especially ordinary host faults and guard-page tests, continue to pass.
- The full FreeBSD =workspace-debug= suite remains green.

*Out of scope*

- WebAssembly stack-switching proposal support (orgbug #1).
- FreeBSD AArch64.
- The related =32 KiB= case tracked separately as orgbug #3; one shared fix may resolve both issues.

* TODO Investigate FreeBSD timeout in parallel Preview 2 sync UDP closed-receiver test :freebsd:
  :PROPERTIES:
  :ID:       b231b674-27b5-495f-879b-4f2e5d82febf
  :ORGBUG_ID: 4
  :CREATED:  [2026-09-16 Wed]
  :END:
*Goal*

Explain and eliminate the parallel-only timeout of =p2::sync::p2_udp_send_to_closed_receiver= on FreeBSD amd64 without hiding the test behind a permanent platform ignore.

*Observed behavior*

- The test timed out when executed as part of the parallel =wasmtime-wasi= test suite on FreeBSD.
- The exact same sync test passes when run alone with =--exact=.
- The Preview 2 async and Preview 3 variants pass.
- The source already documents related parallel flakiness on Windows and macOS. Possible causes noted there include interaction with the async variation, another test rebinding the supposedly closed port, and OS ICMP rate limiting.
- The FreeBSD workflow currently skips only this test in the combined WASI invocation, then runs it separately and requires the isolated run to pass.

*Investigation scope*

1. Establish reproducibility on FreeBSD 14.5 and 15.1 amd64 with repeated full-suite runs.
2. Compare normal parallel execution, =--test-threads=1=, the sync test paired with its async variant, and the sync test paired with other UDP tests.
3. Trace socket addresses, port allocation/reuse, ICMP errors, poll readiness, and timeout behavior to distinguish test interference from a FreeBSD socket or sync-adapter defect.
4. Determine whether the test needs unique port coordination, a stronger close/rebind synchronization point, or a platform/runtime correction.
5. Keep the isolated check until the parallel path is demonstrably stable.

*Acceptance criteria*

- Repeated combined =wasmtime-wasi= runs pass on FreeBSD 14.5 and 15.1 amd64 with this test enabled.
- The =--skip p2::sync::p2_udp_send_to_closed_receiver= workaround is removed from =.github/workflows/freebsd.yml=.
- The dedicated isolated workflow step and its aggregate outcome handling are removed.
- The sync, async, and Preview 3 variants continue to pass individually.
- No unconditional FreeBSD ignore is introduced unless upstream explicitly decides that the underlying OS behavior makes the assertion invalid.
- The full FreeBSD =workspace-debug= suite remains green.

*Out of scope*

- Fixing the existing Windows or macOS flakiness unless the same root cause and fix apply.
- Unrelated UDP disconnect error normalization already covered by the FreeBSD compatibility patch.
- FreeBSD AArch64.
